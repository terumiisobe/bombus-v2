2. FUNCTIONALITY
--------------------------------------------------------------------------------
Planned together. Grouped by behavior.

2.0 Edits are by id
The user types a code. That code is a lookup, not a write key. The chat resolves
it to exactly one colmeia id, loads that row by id, and every update and delete
runs against that id. No UPDATE, no INSERT, and no DELETE in an edit is
predicated on code.

Resolution, membership-scoped, all statuses. Active means the current status
does not release the code. Inactive means perdida or vendida.
- No row for the code → ColmeiaNotFound. Nothing is written.
- The user did not name a status, and exactly one row is active → that id.
  Inactive siblings are not the target. No confirmation.
- The user did not name a status, and no row is active, and exactly one row is
  inactive → that id. The chat confirms once, naming that status, and only then
  writes.
- The user named a status that matches exactly one row → that id. If that row
  is inactive, confirm once before the write. If it is active, do not confirm
  a status change.
- Two or more active rows, or two or more inactive rows and no active row, or
  several rows of a named status → AmbiguousDisposition or AmbiguousCode.
  Nothing is written. The bot asks which status, then resolves again. It does
  not guess the latest row.

Preferring the active hive is the default. The 12:15:50 case has no active
hive: 12345 is only vendida on 999355, so the edit targets that id after one
confirmation, and does not insert 999356. Once an active hive shares the code,
a later status change or delete hits the active id and leaves the inactive one
alone, unless the user names the inactive status. create_colmeia is the only
insert, and only when the user is registering a new hive.

The id never appears in a tool result, a prompt, or a WhatsApp reply. The
confirmation does not include it either.

2.1 Perdida confirmation
Marking an active hive perdida runs in that turn. There is no confirmation
question for that transition. The retained chat does not contain one either;
code 10000 was written perdida once (section 1b). RecordColmeiaStatusService
still appends historico on every successful call, including a same-status visit
(D2). That append stays. In this session it is what stored the note "colônia
forte" on 10301, and it is not a question to the user. The tool and prompt
lines that call that append a confirmation ("mesmo status = confirmação",
"including same-status confirmations") go.

The confirmation that stays is the one in section 2.0: a status change or
delete whose target is already inactive (perdida or vendida) asks once, names
that status, and writes only after the user says yes. One question, not a
second one on top of the hard-delete yes.

2.2 Vendida count
"Quantas vendidas" returns one count per code the owner sold, not a second row
created because the first vendida freed the code.

Production cause (section 1b): at 12:15:04 code 12345 (hive 999355) became
vendida. At 12:15:50 the same code was set to desenvolvendo and a new hive
999356 was inserted, because record/create only sees an active hive and a
vendida row releases the code. At 12:18:30 that new hive was also marked
vendida. Both rows remain. Plus 10300, latest-status vendida is 3 rows and
2 codes. The owner handled one 12345. The count query reporting 3 is the
wrong number they saw. Do not "fix" that by excluding vendida from an explicit
vendida filter.

Also still true, and still fixed in the prompt and the count tool text: the
count use case is include-only when a status is named. Stacking the default
exclusion on top would return zero. list_colmeias has no status argument and,
above 10 hives, answers with a species breakdown whose total does not apply
the default exclusion. "vendidas" is not an exact vocabulary match, so a retry
without status restates the living-herd total. Those paths stay closed. They
are not what inserted 999356.

Verified count-filter behavior, left unchanged:

- CountColmeiasService.toFilter already treats status as include-only. A non-null
  statusId builds ColmeiaCountFilter(includeStatusId = statusId) and leaves
  excludeStatusIds empty. ColmeiaCountFilter rejects include and exclude together.
- ColmeiaCountAdapter applies "status NOT IN (...)" only when hasExclude is true.
  Testcontainers test "explicit vendida status is returnable when the exclusion is
  not applied" counts 1 vendida hive. Unit test "explicit vendida status is
  returnable" asserts includeStatusId = vendida and an empty exclude set.
- breakdown() also leaves exclude empty. An explicit statusId plus groupBy still
  filters with includeStatusId only. A groupBy with no statusId sums every status,
  vendida included. That is intentional for "por status" (the vendida bucket is a
  perStatus line; total is the sum of every bucket).
- The wrong number is produced around that correct query. list_colmeias has no
  status argument. includeLost toggles perdida and vendida together. When the
  default (excluded) plain count is greater than 10, executeList calls count with
  groupBy SPECIES and returns breakdown.total. That breakdown does not apply the
  default exclusion, so the figure includes perdida and vendida while the tool
  text says they are excluded. The system prompt says default counts already
  exclude vendida and never says a named status replaces that exclusion, so a
  turn that omits status restates the living-herd total (excludedStatusLabel
  "perdida, vendida"). ChatVocabularyResolver matches "vendida" exactly;
  "vendidas" is unknown_status. A retry without status is the living-herd total.

Fix, two parts:
- Leave toFilter, breakdown(), and the count SQL as they are. Remove the
  list-as-count tool path (section 2.3). State in the count tool description
  and the system prompt that status "vendida" (canonical vocabulary name,
  including when the user says "vendidas") counts only that status, that total
  is that count, that excludedStatusLabel is absent, and that groupBy is
  omitted for a single-status question. On unknown_status, the model does not
  call count again without the status. Regression tests in steps 2 and 7 lock
  include-only so a later change cannot AND the default exclusion onto vendida
  and return zero.
- A status change resolves the code to one id (section 2.0) and updates that
  row. That is the 12:15:50 case: 999355 is the only hive for the code and it
  is vendida, so the chat confirms once and then sets that id back to
  desenvolvendo. 999356 is not created. create_colmeia still inserts when the
  user is registering a new hive. update_colmeia is what the model must call
  for "código 12345 está desenvolvendo" after a sale. If an active hive already
  shares the code, the status change hits the active id and does not ask.

2.3 Detalhar versus count
Count stays count_colmeias. The user-facing verb for one hive is detalhar.
The Portuguese word "listar" leaves the capability blurb, the fallback help, the
system prompt, and every tool description. list_colmeias leaves the tool list,
including its species_count branch. There is no alias that maps listar onto a
count.

detalhar is one hive. The user says a code; the read uses the same preference
as section 2.0 (the active hive when one exists, otherwise the single inactive
hive) and loads that id. A read does not ask for confirmation. The reply shows
four things and nothing else: code, species common name, current status, and
the last visit. The last visit is the latest historico row (date in
America/Sao_Paulo, its status, its note), the same line shape as section 2.5.
No abbreviation, no scientific name, no meliponário, no start date, no id.

ListOwnedColmeiasUseCase stays compiled. It is no longer a chatbot tool. Do not
delete it in this batch.

2.4 Delete after perdida
DeleteColmeiaUseCase today calls ColmeiaActiveCodeResolver, which drops
perdida/vendida rows. A code that is only perdida throws ColmeiaNotFound. A code
held by an active hive and an older perdida row deletes the active hive
(ColmeiaCrudServicesTest, "delete ignores vendida with the same code and deletes
only the active hive").

New rule: resolve the code with section 2.0, then delete that id.
DeleteColmeiaCommand carries the id, not the code. The port call is
deleteByIdForOwner. An active hive is deleted without an extra inactive
question; the existing one yes (section D-7) still applies. A code that is only
perdida resolves to that inactive id; the one yes names perdida, then that id
is deleted. The user does not have to repeat "perdida" as a status filter.
When an active hive shares the code, the default delete is the active id and
the inactive sibling stays. Naming perdida resolves the inactive id, the yes
names perdida, and the active sibling stays. Status is only an input to
resolution. It is not a column predicate on the DELETE.

2.5 History formatting
The retained chat has no history reply. The visit that has to read cleanly is
the one that was stored: 08/10/2026 12:26 — estavel, note "colônia forte"
(code 10301). History is loaded for the resolved colmeia id (section 2.0), not
for every row that shares the code. list_colmeia_history still returns the use
case's fields only: recordedAt, statusName, note. Newest first. Limit unchanged
(default 10, max 50). The tool JSON formats recordedAt for WhatsApp and adds a
lines array the model pastes. No new history columns, no source, no visitedAt.
Empty history is one Portuguese sentence, not a raw count of zero.

2.6 Softer delete tone
The 8 Oct greeting offers "marcar colmeias como perdidas ou vendidas" and does
not mention excluir. That is the pushiness. Soft disposition stays available.
The prompt and the update/delete tool descriptions stop insisting on it, stop
refusing excluir, and stop redirecting a clear excluir into perdida/vendida.
delete_colmeia stays a real tool. When the user asks to excluir, the model
calls it (after the one confirmed=true check). It does not lecture about
registry mistakes. The first-turn overview names excluir alongside the other
capabilities. Code 10000 is still perdida; this window does not contain the
failed excluir, and section 2.4 is what makes that delete succeed.

3. ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------
Two bounded contexts, already on main. No new service, no new provider, no HTTP
resource. WhatsApp remains the only driving adapter, via the existing tool loop.

  WhatsApp → HandleIncomingWhatsAppMessageService
               → ConversationAiPort (OpenAI adapter; system prompt lives here)
               → ChatToolExecutor
                    → CountColmeiasUseCase          (unchanged filter)
                    → DetailColmeiaUseCase          (new inbound port)
                    → ListColmeiaHistoryUseCase     (unchanged)
                    → resolve code → one colmeia id
                    → RecordColmeiaStatusUseCase    (writes that id)
                    → DeleteColmeiaUseCase          (deletes that id)
                    → DetailColmeiaUseCase          (loads that id)

Count and record stay behind the ports they already have. The AI stays behind
ConversationAiPort; this batch only changes prompt text and tool schemas. Fakes
of those ports cover the application tests. Output quality of tone is locked by
assertions on the prompt and tool descriptions, not by a new eval harness.

Why this shape: the vendida total of 3 counts two rows for code 12345. The
second row was inserted because the edit was keyed by code and the vendida row
no longer counted as that code. Resolving to 999355 and updating that id does
not insert. The count filter stays include-only; putting the default exclusion
back into the SQL would zero an explicit vendida count. The JDBC adapter loads
and writes rows it can already see, by id.

No REST controller is added. No @WebMvcTest. Persistence coverage for the new
read is Testcontainers + @SpringBootTest, the same slice as
OwnedColmeiaAdapterIntegrationTest (JDBC, not @DataJpaTest).

4. KEY DECISIONS & TRADEOFFS
--------------------------------------------------------------------------------
D-1  Where to fix the vendida count
Options: (a) AND the default exclusion onto an explicit status filter;
(b) make breakdown() exclude perdida/vendida unless a status is named;
(c) leave the count use case and SQL, and stop the chat from answering
"quantas vendidas" with the unfiltered total or the list-as-count breakdown;
(d) resolve the code to one colmeia id and update that id, so a status change
never inserts a second row for the same code.
(a) returns zero for vendida: include and NOT IN cannot both match that id.
The domain type already forbids the combination. (b) hides the vendida bucket
from "quantas por status" and breaks the shipped breakdown tests, which sum
every status on purpose. (c) is necessary so the model does not restate the
living herd, and it is not sufficient: a correct row count on 8 Oct is 3,
and the owner was handling one code 12345 (section 1b). (d) is what stops
999356 from being born: the write hits 999355's id. create_colmeia still
inserts, so a deliberate new hive can reuse a sold code.
Recommendation: (c) and (d). Do not change the count SQL. Edits never use code
as the write key (section 2.0).
Flip if the 12:15:50 desenvolvendo was meant as a second hive. Then drop (d)
and accept two vendida rows for one code. The 46-second gap and the owner's
"contagem errada" are why (d) is the default.

D-2  Detalhar versus a renamed herd list
Options: (a) keep list_colmeias, rename the Portuguese word, and still collapse
to a species count above 10 hives; (b) remove that tool and add a one-hive
detail tool.
(a) keeps the alias the owner rejected. (b) makes count and detalhar different
operations. The herd-list use case stays in the binary without a chatbot entry.
Recommendation: (b).
Flip if the owner later wants a paginated herd list under a different verb. That
list must not call count and must not be named listar.

D-3  Which row a status change or delete hits when a code is shared
Options: (a) keep "active only", and a sole inactive code is not found;
(b) always edit the inactive row and spare the active one; (c) prefer the
single active row when one exists; when none exists, the single inactive row,
and the chat confirms once before the write.
(a) cannot change or delete a perdida hive. (b) edits the sold hive when the
user meant the live one. (c) matches the owner: the active hive wins, and the
inactive hive is used only when it is the one that exists, after a yes.
Recommendation: (c), then the write is by that id (section 2.0).
Flip if a shared code should always ask which row. Do not go back to (a).

D-4  Vendida uses the same delete rule
Options: (a) perdida only; vendida stays ColmeiaNotFound; (b) both, via the
existing releasesCode set (perdida, vendida).
The owner confirmed perdida only. Vendida already shares code-release, count
exclusion, and the active-code ignore list. A special case for vendida is a
second resolver. (b) is the recommendation and is what the contracts implement.
Flip if the human says a vendida hive must stay undeletable: then a named
vendida status is ColmeiaNotFound and is not a reason to throw
AmbiguousDisposition. Until that call, implement (b).

D-5  Where history gets pretty
Options: (a) prompt only, model reformats Instant.toString(); (b) format in the
tool JSON from the three fields the use case returns; (c) new columns.
(a) is how the raw dump happens today (date is recordedAt.toString()). (c) is
out of scope. (b) is deterministic and still presentation.
Recommendation: (b). Zone America/Sao_Paulo, pattern dd/MM/yyyy HH:mm, locale
pt-BR. Clock.systemUTC() stays. The formatter converts.
Flip if the deployment is not Brazil: move the zone to a property. Do not store
a local timestamp.

D-6  When a write asks for confirmation
Options: (a) confirm every status change; (b) never confirm a status change;
(c) confirm only when the target hive is already inactive.
(a) adds the turn the owner rejected for marking an active hive perdida.
(b) writes a vendida or perdida hive without the yes they just asked for.
(c) marks an active hive perdida in the same turn, and asks once before
changing or deleting a hive that is already perdida or vendida. The question
names that status. It is one yes, not a second gate on top of D-7.
Recommendation: (c). The historico append still happens on the write, including
a same-status visit. The prompt stops calling that append a confirmation.
Flip if the inactive yes turns out to be the nag they rejected. Then drop it
for status changes and keep D-7 for delete only.

D-7  Hard-delete confirmation
The confirmed=true gate on delete_colmeia stays: one yes, then the tool runs.
The change in this batch is the surrounding copy (section 2.6), not removal of
the gate.
Flip if the owner wants excluir with no yes. Do not remove it in this batch.
